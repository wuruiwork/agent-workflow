# 功能设计与实现

## 职责边界

**只负责：**
- 理解需求并澄清功能目标。
- 创建或更新设计文档；流程内写 `docs/specs/current/00-plan.md`，单独使用时默认 `.tmp/YYYY-MM-DD-<feature-name>.md`。
- 在调用方提供审核通过/用户确认条件后，按文档实现代码。
- 为涉及代码逻辑的改动新增或更新测试文件。
- 更新设计文档状态和实现总结。
- 输出验证建议和风险残留。
- 调用方声明 `task_end` 槽位时，每完成一个实现步骤后通过 `git-action` 提交本步骤改动。

**不负责：**
- 不创建或同步分支。
- 不评分设计文档。
- 不启动或停止运行环境。
- 不执行最终验证门禁。
- 不自行执行 `git add` / `git commit` / `git push`；提交只能通过 `git-action` 按 `task_end` 绑定执行。
- 不推送、不创建 MR、不切换分支。
- 不整理已完成 `.tmp` 文档。
- 不决定下一阶段流程；只把产物返回给调用方。

## 输入

调用方应提供：

- 任务目标和约束。
- 当前任务根目录，普通仓库或 worktree。
- 本次轮次：`design`（只出设计）或 `implement`（按已确认文档实现）；未提供时按文档状态判断（`approved` → 实现轮，其他 → 设计轮）。
- 设计审核/用户确认状态；未确认时本 skill 只产出或更新设计文档并保持 `status: draft`，不写功能代码。
- 可选：设计文档路径。由 `flow-runner` 调度时传 `docs/specs/current/00-plan.md`；未提供时默认 `.tmp/YYYY-MM-DD-<feature-name>.md`。
- 可选：`FLOW`、`FEATURE`，以及调用方声明的 `task_end` 动作（来自 profile 的 `bindings.<stage>.task_end`）；设计轮不执行。

## 强制规则

1. 读取当前 `SKILL.md`，并说明正在使用 `plan-code`。
2. 简单 bug、配置或纯文档修改可拒绝使用本 skill，并返回调用方选择更小流程。
3. 写代码前必须已有明确的设计确认条件：设计文档 `status: approved`，或调用方显式声明用户已确认。没有确认条件时只创建/更新设计文档并保持 `status: draft`，不写功能代码。
4. 设计文档默认写 `.tmp/YYYY-MM-DD-<feature-name>.md`，且必须位于当前任务根目录；流程内由调用方指定 `docs/specs/current/00-plan.md`，以指定路径为准。worktree 场景不得写到主仓库 `.tmp/`。
5. 使用文件编辑工具（Write/Edit）创建或修改文档和代码；整文件新建用 Write，局部修改用 Edit。
6. 实现必须贴合设计文档；偏离方案时先更新文档并说明差异。
7. 不做无关重构。
8. 完成后只输出实现结果、测试/验证建议和风险，不主动进入其他 skill。
9. 设计轮不执行 `task_end`；实现轮若调用方声明了 `task_end` 槽位，每完成一个实现步骤后按「task_end 槽位」一节提交；未声明时不提交。
10. 实现轮开始时确认文档 `status` 为 `approved`；若调用方声明已确认但文档仍为 `draft`，先改为 `approved`。实现并自检完成后改为 `implemented`；未完成实现时保持 `approved`，不要提前标记。设计轮结束时保持 `draft`。

## 两遍执行

供 `flow-runner` 的 `approval: true` 阶段使用，也可在单独调用时按同样规则执行。

- **设计轮**（`PLAN_ROUND=design`）：理解需求、写设计文档，`status: draft`；不写功能代码、不新增测试、不提交、不执行 `task_end`。结束时明确说明“等待用户确认设计”。
- **实现轮**（`PLAN_ROUND=implement`）：仅在 `status: approved` 或调用方明确声明用户已确认时执行；严格按文档实现、补测试、自检，完成后把 `status` 改为 `implemented`。
- 未声明轮次时按文档状态判断：不存在或 `draft` → 设计轮；`approved` → 实现轮；`implemented` → 报告已完成，不重复实现。

## 设计文档模板

```markdown
---
feature: <功能名称>
status: draft  # draft | approved | implemented
created: YYYY-MM-DD
author: Claude
---

# <功能名称>

## 1. 功能概述

目标、价值和成功标准。

## 2. 使用场景

用户、触发条件、主要流程和异常场景。

## 3. 技术方案

### 3.1 架构设计

- 涉及模块/服务。
- 模块边界和交互。
- 数据流向。

### 3.2 关键决策

- 决策内容。
- 替代方案。
- 取舍理由。

### 3.3 影响范围

- 修改文件/模块。
- 兼容性影响。
- 数据库/schema/迁移影响。
- 权限、状态机、后台任务、缓存、消息队列影响。

如涉及数据库，必须列出目标结构：表、字段、类型、默认值、非空、唯一性、外键、检查约束、索引、注释和历史数据处理。

## 4. 实现步骤

按依赖顺序列出实现步骤，不写具体代码。

## 5. 测试策略

- 正常路径。
- 错误路径。
- 边界值。
- 回归风险。
- 需要正式测试文件覆盖的逻辑。
- 可通过 SQL/CLI/HTTP 验证的数据或运行时状态。

## 6. 风险和回滚

风险、监控点、回滚方案。

## 7. 后续优化

本轮不做但值得记录的改进。
```

## 实现规则

- 严格按已确认文档实现。
- 涉及代码行为时优先新增或更新正式测试文件。
- 临时验证脚本放入 `.tmp/verify/` 或项目约定的 ignored 目录。
- 如果项目要求测试文件不上传，确保测试目录被 `.gitignore` 忽略；已跟踪测试需从版本控制撤回但保留本地文件。
- 数据库 schema、seed、hotfix 或运行时数据可以给出 SQL/CLI 验证建议；解析、转换、URL 构建、状态切换、权限判断等代码逻辑应由测试覆盖。

## task_end 槽位（可选）

调用方（`flow-runner`）会传入当前阶段在 `flow.yaml` 声明的槽位和项目 profile 的绑定。只有声明了 `task_end` 时才执行本节。

提交边界是“未验证、未完善的中间步骤”（设计文档「实现步骤」中的一步；大型变更按会话划分时，一个会话算一步），与改动大小无关。完整功能在 review / verify 通过前不 push、不建 MR。

- **动作来源**：`bindings.<stage>.task_end`；只允许 `commit`。出现 `push` / `mr` 时停止并报告，不执行任何动作。
- **提交时机**：一步的代码、测试、自检和设计文档进度都完成后，调用 `Skill(git-action)`，传入：
  - `ACTION=commit`
  - `STAGE=<当前阶段，例如 plan>`
  - `FLOW=<流程名>`
  - `FEATURE=<feature>`
  - `SCOPE=<本步骤涉及的文件路径列表>`，只提交本步骤范围。
- **成功**：记录 commit sha，继续下一步。
- **失败**：`git-action` 报错或报告范围外改动时停止，原样报告，不重试、不跳过、不继续下一步。
- **未声明或绑定为空**：不提交，由阶段结束的 `stage_end` 动作统一处理。
- 本 skill 不直接执行 git 命令；`push` / `mr` 不在步骤级发生。

## 大型变更划分

当设计文档涉及多个模块、跨仓库修改，或预计改动文件超过 10 个时，在设计文档中按会话拆分：

```markdown
## 4. 实现步骤（会话划分）

### 会话 1：<模块名>
**前置条件**：<无 / 依赖项>
**目标**：<本会话完成什么>
1. ...

### 会话 2：<模块名>
**前置条件**：会话 1 完成
**目标**：<本会话完成什么>
1. ...
```

每个会话应能独立说明产物和验证建议。

## 完成输出

完成后必须输出：

- 设计文档路径。
- 文档状态。
- 本次轮次（`design` / `implement`）。
- 设计轮：等待用户确认的说明；不输出实现摘要，不产生 `task_end` 提交。
- 实现轮：修改文件列表、实现摘要、与设计差异、新增/更新的测试、每个实现步骤的 commit sha（`task_end` 生效时）。
- 建议验证命令或验证点。
- 风险残留和阻塞点。
