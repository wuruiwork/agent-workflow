# 验证门禁（df-verify）

## 职责边界

**只负责：**
- 建立验证矩阵：需求成功标准、设计约束、任务验收项 → 验证方式 → 证据。
- 读取项目已有命令，运行测试、构建、lint、类型检查等验证。
- 核对实现与设计的一致性。
- 创建或更新 `docs/specs/current/40-verify.md`。
- 给出 `pass` / `fail` 结论和失败归因。

**不负责：**
- 不修改功能代码。
- 不修改测试断言使其通过。
- 不修改设计文档、任务清单、实现记录。
- 不新增依赖、不引入新的测试框架或工具。
- 不提交、不推送、不创建 MR。
- 不归档文档。
- 不做性能压测、安全审计等未在设计中约定的专项验证（除非用户明确要求）。

## 输入

- `docs/specs/current/00-brief.md`（成功标准）。
- `docs/specs/current/10-design.md`（约束、测试策略；inline 时读 brief 第 9 节）。
- `docs/specs/current/20-tasks.md`（验收标准、任务状态）。
- `docs/specs/current/30-impl.md`（改动清单、自检结果、偏离记录）。
- `docs/specs/current/35-review.md`（完整流程必需；inline 跳过审查时不存在）。
- 当前代码和工作区。

## 前置条件

- `20-tasks.md` 中所有任务均为 `done`，或用户明确指定验证范围。
- `30-impl.md` 存在且 `status: done`。
- 完整流程：`35-review.md` 存在且 `status: pass`；inline 跳过审查时，`40-verify.md` 需记录 `review: skipped` 及原因。
- 实现未完成时只输出阻塞原因，不开始验证。

## 强制规则

1. **先建矩阵，再执行**。每条验证项必须能追溯到需求、设计或任务中的具体条目。
2. 验证命令优先取自：项目 README、Makefile、`package.json`、`pyproject.toml`、CI 配置、CLAUDE.md；不擅自发明命令。
3. 只使用项目已有依赖和工具；缺少必要命令时标记 `blocked`，写清原因和替代验证方式，**不得默认通过**。
4. **只读代码和文档**；不修改功能代码、测试断言、设计、任务状态。
5. 检查工作区状态，记录验证时的 commit（如有）和未提交改动；验证结论只对应当前工作区。
6. 任何一条**必验项**失败 → 结论 `fail`。不得用“大部分通过”“问题不大”放行。
7. 可选项、建议项、非阻塞问题单独列出，不影响结论，但必须在报告中可见。
8. 失败项必须给出：复现步骤、期望、实际、证据、建议退回阶段（`df-implement` / flow-runner 的 design / brief 阶段）。
9. 全部必验项通过后才能把 `40-verify.md` 设为 `pass`；存在残留风险时，先在输出中显式列出并等待用户确认，确认后再落 `pass`。
10. 验证脚本放 `.tmp/docfirst/scripts/`，不写入源码目录。
11. 代码级的设计与实现一致性以 `35-review.md` 为证据；本 skill 只复核影响验收标准的偏离，不重复逐行审查。

## 验证矩阵

至少覆盖：

| 来源 | 验证内容 | 方式 |
|---|---|---|
| brief 成功标准 | 每条成功标准 | 测试 / 命令 / 手工观察 |
| 设计约束 | 接口、兼容性、schema、权限、状态机 | 测试 / schema 检查 / 代码核对 |
| 任务验收标准 | 每个任务的 checklist | 测试 / 命令 / 运行时检查 |
| 回归 | 设计中列出的回归风险 | 相关测试套件 |
| 差异 | 实现与设计是否一致 | 引用 `35-review.md`，复核影响验收的偏离 |
