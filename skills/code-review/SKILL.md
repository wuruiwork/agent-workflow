# 代码审查（code-review）

## 职责边界

**只负责：**
- 确定审查基线，界定“本次改动”的确切范围。
- 逐文件读取改动及其上下文，做正确性、数据、接口、安全、设计一致性审查。
- 过滤误报，只保留能说清触发场景的问题。
- 输出带严重级别的审查报告和 `PASS` / `BLOCKED` 结论。

**不负责：**
- 不修改代码、不改测试断言。用户明确要求“审完直接修”时才在报告后另行处理；在 df 流程中被调用时，即使发现问题也只输出报告，不直接修复。
- 不运行测试、构建、lint、类型检查（交给 df-verify 或用户）。
- 不提交、不推送、不创建 MR、不在 GitHub 上发评论。
- 不评审历史遗留问题，只评审本次改动引入的问题。
- 不评价需求本身是否合理（那是 flow-runner 的 brief 阶段）。
- 不维护任务状态、不推进流程（由 flow-runner / df-implement 负责）。

## 输入

- **审查范围**：默认 `git diff` 相对分叉基点；也可指定 commit 区间、文件列表、PR 编号。
- **需求/设计文档**：可选。若存在 `docs/specs/current/`，自动读取 `00-brief.md`、`10-design.md`、`20-tasks.md` 作为一致性基准。
- **关注点**：可选。用户点名只审安全 / 只审性能时，相应收窄范围。

## 强制规则

1. 开始前说明正在使用 `code-review` skill，并先确定审查基线。
2. **必须先确定基线再读代码**：用 `git merge-base` 或用户指定的区间，避免把已合入的历史改动算进本次审查，也避免漏审未 stash 的工作区改动。
3. **基线必须包含未跟踪文件**：`git diff` 只覆盖已跟踪改动，需用 `git status --porcelain` 补充新增文件；无可用 merge-base（如 detached HEAD）时，用 `git diff HEAD` + 未跟踪文件，并在报告中注明基线口径。
4. **必须读完整文件上下文**，不能只看 diff 片段。只看 diff 得到的问题绝大多数是误报。
5. 每条问题必须同时具备：**准确位置（file:line）+ 触发场景（具体输入或状态 → 错误结果）+ 为什么是问题**。三者缺一就不写。
6. 位置行号必须来自实际读取的文件内容，不得估算或拼凑。
7. 存在设计文档时，必须逐条核对设计与实现的一致性，写清哪些已对齐、哪些偏离。
8. 结论只有两种：`PASS`（无 P0/P1）和 `BLOCKED`（存在任一 P0/P1）。P2/P3 不阻塞。
9. 报告默认写入文件；终端只输出结论摘要和问题标题列表，不重复全文。
10. 复审使用与首次相同的基线，在报告中追加「复审记录」并保留上一轮结论；`status` 只反映最新一轮。
11. 在 df 流程中被调用时，不修改 `20-tasks.md` 的任务状态，也不修改代码；退回动作由调用方执行。

## 严重级别

| 级别 | 定义 | 阻塞 |
|---|---|---|
| P0 | 数据损坏、安全漏洞、线上崩溃、静默返回错误结果 | 是 |
| P1 | 明确功能缺陷，或与已确认设计不符，正常路径可触发 | 是 |
| P2 | 边界/异常场景缺陷、潜在性能问题、错误处理缺失但不致命 | 否 |
| P3 | 可读性、命名、注释、重复代码 | 否 |

## 审查维度

按以下顺序扫，每项都对照改动行：

1. **正确性**：边界值、空值/None、并发与竞态、错误处理分支、资源释放、提前返回遗漏、循环与终止条件。
2. **数据**：schema/迁移/索引/约束、事务边界、序列化格式、默认值、历史数据处理。
3. **接口与兼容性**：函数签名、返回值、异常类型、对外协议、调用方是否同步更新、废弃行为。
4. **安全**：注入、越权与权限判断顺序、密钥/凭证硬编码、日志泄露敏感信息、路径穿越、反序列化。
5. **设计一致性**（有设计文档时）：设计中的关键决策是否落地、影响范围列出的文件是否都改了、是否有超出设计的额外改动。
6. **可维护性**：只报实质性的重复、死代码、错误命名；纯风格偏好不报。

## 误报过滤

以下一律不写进报告：

- 本次改动之前就存在的问题。
- linter、类型检查器、编译器会抓的问题（未使用 import、类型不匹配、格式）。
- 无具体触发场景的推测（“这里可能有并发问题”但说不出什么情况下会错）。
- 纯风格偏好，且项目没有明确约定（CLAUDE.md、lint 配置、周边代码惯例）。
- 用户明显有意的改动，即使做法不同（如刻意简化、刻意保守）。
- 只影响测试覆盖率、文档完整性的泛泛建议。
- 被 `# noqa` / `// nolint` / `@ts-expect-error` 等显式抑制的问题。

## 执行流程

1. 确定基线：`git status --porcelain`（含未跟踪文件）、`git diff --stat`、`git merge-base`，得出改动文件清单和增删行数。
2. 若存在 `docs/specs/current/`，读取需求与设计文档；否则跳过第 5 维度。
3. 逐个改动文件读取完整内容及相关调用方。
4. 按审查维度扫描，记录候选问题。
5. **逐条自证**：为每个候选构造具体触发场景；构造不出来的删除。确认不是既有问题。
6. 定级、去重、合并同类项。
7. 产出报告。

## 产物

**文档先行流程中**（存在 `docs/specs/current/`）：

写入 `docs/specs/current/35-review.md`。

**独立使用时**：

写入当前任务根目录 `.tmp/review/YYYY-MM-DD-<slug>.md`；`.tmp` 不可写时直接在终端输出。

### 报告模板

```markdown
---
feature: <feature 或 无>
status: pass  # pass | blocked
created: YYYY-MM-DD
author: Claude
baseline: <merge-base 或 commit 区间>
scope: <n 个文件，+a/-b>
---

# 代码审查：<feature 或 改动摘要>

## 结论

<PASS / BLOCKED> — <一句话说明>

## 问题清单

### P1-1 <标题>

- 位置：`path/to/file.ts:42`
- 问题：<具体描述>
- 触发场景：<输入/状态 → 错误结果>
- 建议：<怎么改，不给完整实现>
- 依据：<设计文档 3.2 / 任务 4 / 通用正确性>

## 已检查未发现问题

- 正确性：<结论>
- 数据：<结论 / 不涉及>
- 接口与兼容性：<结论>
- 安全：<结论>
- 设计一致性：<逐条对齐情况 / 无设计文档>

## 需要回退的任务

<任务编号 + 原因；无则写“无”>

## 复审记录

> 仅复审时保留。首次审查写“无”。

| 轮次 | 日期 | 基线 | 结论 | 已关闭问题 | 新增问题 |
|---|---|---|---|---|---|
| r1 | YYYY-MM-DD | <baseline> | BLOCKED | - | P1-1 |
```

## 终端输出

```
正在使用 code-review skill
审查基线：<merge-base / 区间>，<n> 个文件 +a/-b
结论：PASS / BLOCKED
P0：<标题列表 或 无>
P1：<标题列表 或 无>
P2/P3：<n> 条（见报告）
报告：<路径>
```

## 与 df 流程的衔接

- 审查在 `df-implement` 完成、`df-verify` 之前执行，是 doc-first 流程中的强制门禁；inline 小改动是否跳过由 flow-runner 判定并在 `40-verify.md` 留痕。
- 结论 `BLOCKED` 时，报告列出「需要回退的任务」，由调用方退回 `df-implement`；若偏离原因是设计本身有误，由调用方改走 flow-runner 的 design 阶段。本 skill 不修改 `20-tasks.md` 的任务状态。
- 结论 `PASS` 时，把 `35-review.md` 交给 `df-verify` 作为「实现与设计一致」维度的证据。
- 环境缺少对应 `df-*` skill 时按独立模式运行，产物仍写 `35-review.md`（若目录存在）。
